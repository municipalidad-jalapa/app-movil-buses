3) PRUEBAS MANUALES CON DATOS REALES
-----------------------------------------------------
Estado: PARCIAL. Se consiguio el backend real (api-buses-jalapa) y se probo
por API directa (curl/node), sin navegador. El checklist M1-M12 completo
(que requiere navegador/dispositivo) sigue pendiente para QA.

Lo que SI se ejecuto contra el backend real, actualizado 2026-09-09:

  - Se levanto el backend con docker compose (PostGIS + Spring Boot),
    Flyway aplico sus 7 migraciones sin errores.
  - mvn test del backend: 179/179 PASO, BUILD SUCCESS (incluye sus propios
    escenarios de aceptacion en Cucumber).
  - GET /api/v1/rutas -> 200 OK. Devuelve "Ruta de ejemplo - Centro de
    Jalapa" con 8 paradas reales (Parque Central, Mercado, El Calvario,
    Terminal, Llano Grande, Hospital, Instituto, Chipilapa).
  - GET /api/v1/rutas/1/resumen -> 200 OK.
  - POST /api/v1/reservas (parada 1) -> 201 Created. El conteo en
    reservasActivas subio de 0 a 1 para esa parada en el siguiente
    /resumen. Confirma que el flujo de reservas real funciona de punta a
    punta.
  - GET /api/v1/rutas/1/eta (endpoint de esta historia) -> 404 Not Found.
    NO esta implementado en este backend todavia.
  - GET /api/v1/rutas/1/reservas/activas (endpoint de esta historia) ->
    404 Not Found. NO esta implementado en este backend todavia.
  - POST /api/v1/auth/conductor -> 401, pero es el denyAll() generico de
    Spring Security (SecurityConfig.java), no un controlador real: no
    existe ningun AuthController de conductor en el codigo. El login de
    conductor con Firebase (SCRUM-134) sigue sin construirse.

Conclusion importante: el panel de HU-75 no se puede probar de punta a
punta (login real -> panel con datos reales) contra ESTE backend, porque le
faltan dos piezas del lado del backend:
  1) El login del conductor (`POST /api/v1/auth/conductor`, SCRUM-134).
  2) Los dos endpoints del contrato de esta historia
     (`GET /rutas/{id}/eta` y `GET /rutas/{id}/reservas/activas`).
Esto NO es un defecto del frontend: el frontend ya esta listo para
consumirlos en cuanto existan (ver `src/hooks/usePanelConductor.ts`).

Hallazgo de forma de datos (para quien implemente el backend):
El endpoint ya construido que mas se parece (`/rutas/{id}/resumen`,
SCRUM-284) modela "reservas activas por parada" como una LISTA de objetos
`{paradaId, reservasActivas}` mas un `calculadoEn` en la raiz, NO como un
mapa/diccionario. El tipo `ReservasActivasPorParada` de este frontend
(`src/core/tipos.ts`) usa un mapa (`porParada: Record<string, number>`)
porque, al momento de escribirlo, no existia un contrato real que copiar.
Si el backend reutiliza ese mismo patron para
`/rutas/{rutaId}/reservas/activas` (lo mas probable, por consistencia con
el resto del modulo `demanda`), el tipo del frontend habria que ajustarlo
a una lista antes de integrar. Se deja como hallazgo, no se cambia el
contrato sin que el equipo lo confirme.

Que se entrega para lo que falta: el checklist completo (M1 a M12) en
README.md, listo para que el equipo de QA lo ejecute con navegador contra
un backend real cuando esas dos piezas existan.
